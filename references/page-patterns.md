# 同一个项目，不同页面讲什么

先弄清这位读者准备拿解释做什么。熟悉分布式系统的人第一次看这个仓库，可能已经很懂重试，却仍想知道本项目用哪个键识别重复提交。沿用读者掌握的概念，解释这个项目为它赋予的具体含义。

## 首页给人一个记得住的解释

先定位软件在系统中做的那份工作，再从真实入口挑一处能体现设计选择的行为。有些库只需展示调用前后的一小段数据。多包仓库可以从应用的一个入口说起，在职责发生交接时引入包名。想接入的人可以直接去看公开接口和约束，准备改代码的人则可以从关键实现和测试继续读。多个链接支持同一判断时，可放在小节末并写明它们分别能证实什么。

## 同一处源码，两种读者怎样讲

以 Pi 的文件读取为例。下面两段回答同一个问题：模型要求读 README，究竟由谁取回内容？

**面向初次读 Pi 的工程师。** 模型回复里出现 `read` 调用时，README 的内容还没进入对话。`pi-coding-agent` 提供读取工具，默认负责打开本机文件。`pi-agent-core` 负责推进对话，把工具返回的内容作为一条 `toolResult` 消息加入上下文。模型下一轮能引用 README，靠的就是这条消息。这也说明应该去哪里排查：文件读对了，下一轮却没收到原文，就值得沿工具结果回到上下文的路径查下去。[默认文件操作](https://github.com/earendil-works/pi/blob/0ab23c37b074252d04e31f5cfb99491f0613fb80/packages/coding-agent/src/core/tools/read.ts#L68-L73) · [结果消息的字段](https://github.com/earendil-works/pi/blob/0ab23c37b074252d04e31f5cfb99491f0613fb80/packages/agent/src/agent-loop.ts#L933-L945) · [结果写入上下文](https://github.com/earendil-works/pi/blob/0ab23c37b074252d04e31f5cfb99491f0613fb80/packages/agent/src/agent-loop.ts#L267-L286)

**面向正在接入远程工作区的 SDK 工程师。** 对话循环接收的仍是 `toolResult`。要换的是 `read` 取得字节的方式。`createReadToolDefinition` 优先使用调用方传入的 `operations`，没有提供时才选择本机实现。实现 `ReadOperations` 时，文件可读性检查和内容读取都要对准同一个远程工作区，否则工具可能在取内容之前就因路径检查失败。由此可知，改造的入口在工具侧，循环仍然按原契约消费结果。[操作接口和本机默认值](https://github.com/earendil-works/pi/blob/0ab23c37b074252d04e31f5cfb99491f0613fb80/packages/coding-agent/src/core/tools/read.ts#L49-L73) · [选择读取实现](https://github.com/earendil-works/pi/blob/0ab23c37b074252d04e31f5cfb99491f0613fb80/packages/coding-agent/src/core/tools/read.ts#L229-L237) · [开始读取前的检查](https://github.com/earendil-works/pi/blob/0ab23c37b074252d04e31f5cfb99491f0613fb80/packages/coding-agent/src/core/tools/read.ts#L265-L272)

前一段帮读者找到数据经过的边界；后一段让接入者找到可替换的接口和一个可能踩到的条件。两种写法都保留了结果消息这个关键事实。选细节时可以用同样的判断：它能帮助眼前这位读者作出什么决定？

## 架构讲分工，流程讲变化

**在架构页**，选择能解释整体的边界。也许是本机与服务端，也许是编译时与运行时，也许是框架与调用者之间的契约。用仓库实际采用的名字标明参与者，再写清它们为何要打交道、交付什么。图上两个节点如果只是同一进程里的库，要交代这一点，以便读者判断调用成本和故障位置。

**在流程页**，沿一个输入往前走。哪一步做出了会改变结果的决定？下一方拿到什么，才有办法继续做事？回到 Pi 的例子，「模型为什么要等文件读完」比逐个介绍消息传递函数更值得停下来讲。结尾回到最初的问题，让读者知道此时屏幕上会出现什么。真实执行可能有多个结果时，正文交代与例子有关的条件，其他分支链到对应专题。

小标题要能连起来读。假如一篇流程从“接到问题”直接跳到“输出结果”，中间最值得解释的可能恰好是“模型怎样拿到 README 里的那一行”。问句适合引出这个疑惑，下一节可以直接给判断，例如“第二轮才有文件里的原文”。读者扫一眼右栏，就能知道这篇文章把问题讲到了哪里。

## 快速开始只带读者走到第一个结果

选一个能在正常入口完成的小任务，交代它需要的环境，接着给最短可复制的操作和辨认成功的方法。对于 CLI，这是一次调用及其可见输出；对于库，可能是一个返回值；对于前端，可能是界面里一项能看见的变化。只有可能拦住这次尝试的条件才值得在这里说。需要外部账号、模型或服务时，如实写明前提和哪些步骤实际验证过。

## 专题写到足以解决问题的深度

专题从主线留下的一个疑问起步。比如读者昨天关掉程序，今天想接着做，最先要知道的就是哪些东西还能找回来。先回答这一点，再解释记录存在哪儿、何时写入，以及哪种中断会影响恢复。一个异常如果会让读者选错操作，应留在这里。其余限制可以在对应参考页查。

接口表适合让已经决定动手的人查参数、默认值和适用条件；维护页适合从一个症状找到受影响的行为、代码和测试。写参考时可以精确到函数和数值。涉及外部依赖或设计动机时，要交代证据所能支持的范围。源码解释不了作者动机，往往能解释某种选择给使用者带来的后果。

## 换一种仓库，入口也要换

读库或 SDK，可以跟一次在调用方看得见的返回、错误或回调。读服务，从一次请求引起的状态变化入手。读编译器或数据工具，一小段输入怎样变成输出，往往就足以串起几层实现。读框架或插件宿主，则可以追谁把控制权交给用户代码。对于规范、配置或资料库，挑一条真实的使用或查询路径。选能代表这个仓库的一例，写完后再判断哪里值得单独成篇。
